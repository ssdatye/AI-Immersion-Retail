1. Summary

The team's demo approach works and has no blockers. It runs a real agent (Microsoft Agent Framework on App Service, with a Foundry-hosted model) over illustrative data in Azure SQL and Cosmos DB. Dana and Luis sign in with their own Entra accounts. Production keeps the same building blocks but adds private networking, an API gateway, live data integration, governance, and separate dev/test/prod environments.

2. Review of the demo strategy

#DecisionVerdictRecommendation
1Lightweight JavaScript front endFineUse Vite with React or Preact, or keep the current vanilla JS studio. Serve it from the same App Service as the API so you have one URL and one sign-in.
2Data in CSV, Azure SQL or Cosmos DBFine; pick a role for eachAzure SQL holds the structured cost facts (orders, routes, fuel, zones), because what-if maths and SUMs suit SQL. Cosmos DB holds agent threads, scenario snapshots and the decision log. Keep the CSVs only as the seed source.
3Microsoft Agent Framework agent on App ServiceFineExpose the cost engine as tools (functions) the agent calls, such as get_cost_per_order, run_scenario, check_guardrail and log_decision. The numbers then come from code, not from the model. Use managed identity to reach Foundry, SQL and Cosmos.
4Foundry for the modelFineDeploy GPT-4.1 or GPT-4.1-mini (Global Standard). Turn on content filters. Keep prompts and tool schemas in source control.
5No Teams; sign in as Dana and LuisFineRegister one Entra app with app roles (FinanceAnalyst for Dana, RegionalOps for Luis). Use App Service authentication (Easy Auth) or MSAL. The API reads the role and region claims to choose the dashboard and filter the data, for example Luis sees Southeast only. Approvals happen inside the studio and are written to the decision log.
Watch-outs (not blockers):
  1. Create the demo users in a non-customer dev tenant, give them MFA, and don't use real Walmart names or data.
  2. Check that Foundry model quota exists in your region before tomorrow.
  3. Keep the scripted fallback from the HTML demo in case the model or network fails live.
  4. Pre-warm the App Service: use B2 or higher with Always On.

Key design principles

  • Numbers come from tools, not the model. Every cost, scenario or guardrail value is computed by the code or SQL tools and quoted by the agent with its source.
  • People approve. Agents recommend. Approvals are role-checked, logged in Cosmos DB with who, what, when and the evidence, and pushed to the TMS/OMS only through APIM after approval.
  • Least privilege. Managed identities everywhere. Row-level security by region in SQL. No public endpoints on data or AI services.
  • Fits Walmart's multi-cloud estate. Read through OneLake shortcuts or APIs where data already lives; don't duplicate systems of record.
  • Resilience. Zone-redundant app and data tiers. Foundry Global Standard for model availability. Point-in-time restore for SQL and continuous backup for Cosmos.

6.4 What drives the cost

  • Model tokens: they scale with users × questions × context size. Routing simple turns to the mini model and caching prompts can cut 30–60%. This is an estimate to test.
  • Fabric capacity: it is fixed. If Walmart already has Fabric capacity, this item may be shared and drop away.
  • High availability: zone redundancy roughly doubles app-tier cost. That is a choice to agree with Walmart.
Value context (scenario, not a forecast): 5% of Walmart's stated "more than $2 billion" extra fuel cost would be about $100M a year. Against that, build plus first-year run would pay back in about 8 days. Confirm the baseline cost per order with Walmart before using this.
