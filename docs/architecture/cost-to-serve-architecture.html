1. Summary

The demo is built and running on Azure. Dana (Fulfillment Finance) and Luis (Southeast Regional Delivery Ops) sign in with their own Entra accounts to one web app, the What-If Studio. A Microsoft Agent Framework (MAF) agent runs inside that app. It answers what-if questions by calling seven tools over a deterministic cost engine, so every number comes from code, not from the model. The model is gpt-4.1-mini in Microsoft Foundry, reached through an API Management AI gateway. Cost facts live in Azure SQL; decisions and chat transcripts live in Cosmos DB. Every service call uses managed identity: the deployment has no keys or passwords.

Both personas use the same app and the same tools. What differs is the role and region in their token, which the API turns into the scope of every tool call.

5. Technology choices and why

5.1 Why a self-hosted Agent Framework agent, not a Foundry-hosted agent

Decision: the agent runs inside the studio's own process on App Service, built with Microsoft Agent Framework. It is not deployed to Foundry Agent Service, either as a prompt agent or as a hosted agent.

The deciding reason: the agent is a feature of this application, not a standalone service. Every tool call must run as the signed-in person, under the same authorization, workflow and data as the studio's buttons, and it must be able to pause for that person's confirmation. That puts the agent inside the application's trust boundary. In process, the host builds the tools for the caller from the validated token (role and region), and the model never sees or supplies an identity. The UI and the agent share one implementation of the decision rules.

The other Foundry options would move the agent outside the application:

What we give up: managed per-session isolation and scaling, platform-managed conversations, agent versions and rollback in the Foundry portal, a dedicated agent identity, and publishing to Teams or Microsoft 365 through the Activity protocol.

When to revisit: if the agent must serve other channels (Teams, Microsoft 365 Copilot) or many apps. The MAF code ports to a Foundry hosted agent (Responses protocol) largely unchanged. The tools would then sit behind an APIM-protected tools API that accepts the user's token on-behalf-of, so scope still comes from the user and not the model.

  • No keys: local auth is off on Foundry, Cosmos DB and App Insights; SQL accepts Entra tokens only; App Service basic publishing credentials are off.
  • Ingress: the App Service denies everything except the APIM IP address. The AI gateway accepts only the studio identity's token.

  • Isolation: everything is in one dedicated resource group; nothing else in the subscription is read or changed.

7. Observability and quality

  • Tracing: spans from ASP.NET Core, HttpClient, MAF (Microsoft.Agents.AI*, Experimental.Microsoft.Extensions.AI) and the studio (CostToServe.Agent, CostToServe.Chat). Each tool span records the caller's role, scope and outcome. APIM adds its own spans with W3C correlation and no request or response bodies.
  • Chat transcripts: each turn (question, answer, tools used, trace ID) goes to Cosmos threads, ready for evaluation datasets.
  • Trust Center: a studio tab shows the last evaluation run, this session's live evidence for the caller's own answers, the span timeline of the latest answer (request, agent, model, tool; the time spent waiting for a person's confirmation is shown separately) and the controls in force, with links to Foundry and Application Insights. Under every answer, a receipt traces each quoted number to the tool field it came from, using the same check as the evaluation (NumberEvidence), or shows a refusal by policy or a confirmed decision. Session data is in memory per instance; Application Insights stays the record. See ADR 006.
  • Tests: 144 .NET tests cover engine parity (472 golden cases from the reference HTML), the demo anchors (Southeast Express $15.56 to $17.01; +$0.50 for 13 weeks ≈ $28.2M; A1 + A2 offset ≈ 88%), tool scope, the decision workflow by role and region, the API, the Trust Center and live evidence, and the evaluation checks. 19 web tests cover commands, levers, waiting items and evidence receipts. No unit test calls the model.
  • Agent evaluation: ./scripts/run-evals.sh asks 27 questions as Dana and Luis through the studio's agent code. A .NET runner checks tool selection, numbers against the engine, that every quoted number comes from a tool, and the decision rules. The same turns go to Foundry judges (task adherence, tool-call accuracy, intent resolution, groundedness) in the isolated proj-evals project. Latest result: 27 of 27 cases pass the deterministic checks; the only judge failures are tool calls the tools refused by design. See docs/evals/report.md and ADR 005.
